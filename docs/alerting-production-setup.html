Production Alerting Setup

The alert rules and routing are built and committed; what remains is human configuration — wiring a real receiver, pointing the scrape at the production app, and connecting the backup metric. Complete this before the soak so a real outage actually pages.

← Dashboard← R2 Setup

Already in the repo (deploy/observability/): Prometheus rules (prometheus-alerts.yml), Alertmanager routing (alertmanager.yml), blackbox /readyz module, Grafana dashboard, and a one-command stack (docker-compose.observability.yml: Prometheus 2.54 · Alertmanager 0.27 · blackbox 0.25 · node-exporter 1.8). Every alert expression references a metric the app actually emits.

2 · Wire a real receiver (the SEV-1 gate)

Edit deploy/observability/alertmanager.yml. Routing is already correct (page → urgent repeat 1h; ticket → default repeat 4h). Replace the receivers — pick one channel.

Slack

receivers:
  - name: default
    slack_configs:
      - api_url: "https://hooks.slack.com/services/XXX/YYY/ZZZ"
        channel: "#qr-dining-alerts"
        send_resolved: true
        title: '{{ .CommonAnnotations.summary }}'
        text: '{{ range .Alerts }}{{ .Annotations.description }}{{ "\n" }}{{ end }}'
  - name: urgent
    slack_configs:
      - api_url: "https://hooks.slack.com/services/XXX/YYY/ZZZ"
        channel: "#qr-dining-pager"
        send_resolved: true

PagerDuty (for page severity)

  - name: urgent
    pagerduty_configs:
      - routing_key: "<PD_INTEGRATION_KEY>"
        send_resolved: true

Email

  - name: urgent
    email_configs:
      - to: "oncall@yourdomain.com"
        from: "alerts@yourdomain.com"
        smarthost: "smtp.yourprovider.com:587"
        auth_username: "alerts@yourdomain.com"
        auth_password: "<SMTP_APP_PASSWORD>"
        send_resolved: true
Keep secrets out of git: reference them via env in the Alertmanager container or a mounted secret file, not committed inline.

3 · Connect the backup metric

The BackupFailed / BackupTooOld alerts read qr_dining_backup_* gauges that nightly-backup.sh writes to the node-exporter textfile collector. Point both at the same shared volume.

# in /etc/qr-dining/backup.env
NODE_EXPORTER_TEXTFILE_DIR=/var/lib/node_exporter/textfile_collector

# node-exporter must read that same directory (the observability compose already
# mounts a backup_textfile volume at /var/lib/node_exporter/textfile via
# --collector.textfile.directory). Ensure the backup writes into that volume.

4 · Deploy the stack

cd deploy/observability
docker compose -f docker-compose.observability.yml up -d
# Prometheus :9090 · Alertmanager :9093 · blackbox :9115 · node-exporter :9100
Do not expose Prometheus/Alertmanager publicly. Bind them to the private/monitoring network or put them behind auth. Keep the soak's app reachable to Prometheus on the shared docker network so up{job="qr-dining"} and the /readyz blackbox probe resolve.

5 · Verify before the soak

# (a) Rules + config parse cleanly.
promtool check rules deploy/observability/prometheus-alerts.yml
amtool check-config deploy/observability/alertmanager.yml

# (b) Targets are UP (after deploy): Prometheus UI → Status → Targets, or
curl -s localhost:9090/api/v1/targets | grep -o '"health":"[a-z]*"' | sort | uniq -c
# expect job qr-dining = up, qr-dining-readyz = up, node = up

# (c) Fire a synthetic alert end-to-end and confirm it lands in the real channel.
amtool alert add testfire severity=page alertname=PipelineTest \
  --alertmanager.url=http://localhost:9093 \
  --annotation=summary="alerting pipeline test — please ignore"
# Confirm receipt in Slack/PagerDuty/email, then it auto-resolves.
