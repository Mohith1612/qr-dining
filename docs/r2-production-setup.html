Cloudflare R2 — Production Setup

Provision real R2 storage for (1) database backups and (2) guest image uploads, then verify both with live round-trip tests before the release-candidate soak.

Two distinct R2 configurations. The app and the backup script use different env-var names and should use different buckets. Don't merge them.

Image uploads are optional for the soak (upload endpoints return 503 if unconfigured). DB backups are required — they are the SEV-1 "live R2 round-trip" gate.

1 · Bucket creation

In the Cloudflare dashboard → R2 → Create bucket (or via Wrangler). Use the production jurisdiction nearest the pilot (e.g. APAC). Create both:

# Wrangler (or use the dashboard "Create bucket" button)
wrangler r2 bucket create qr-dining-backups
wrangler r2 bucket create qr-dining-uploads

# Recommended: a 14-day lifecycle rule on the backups bucket as a backstop to
# the script's own retention (RETENTION_DAYS). Dashboard → bucket → Settings →
# Object lifecycle rules → Delete objects 14 days after creation.

2 · API token creation

Cloudflare dashboard → R2 → Manage R2 API Tokens → Create API Token.

  1. Permissions: Object Read & Write — covers PutObject, GetObject, DeleteObject, ListBucket (the script uploads, lists for retention, deletes old dumps, and downloads for restore).
  2. Scope: apply the token to only the two buckets above (not "all buckets"). Prefer two separate tokens — one per bucket — so a leaked uploads key can't touch backups.
  3. TTL: no expiry for the long-lived backup token (rotate quarterly), or a long TTL with a calendar reminder.
  4. On creation Cloudflare shows the Access Key ID, Secret Access Key, and the S3 endpoint https://<ACCOUNT_ID>.r2.cloudflarestorage.com. Copy all three now — the secret is shown once.
The Account ID is in the R2 overview page URL and the endpoint host. The app builds its endpoint as https://<R2_ACCOUNT_ID>.r2.cloudflarestorage.com (see internal/storage/r2.go); the backup script takes the full R2_ENDPOINT.

3 · Environment variables

A · Database backups — /etc/qr-dining/backup.env (root-only, chmod 600)

Consumed by the systemd timer / cron that runs nightly-backup.sh. Template: deploy/backup/backup.env.example.

DATABASE_URL=postgres://qrdining:<STRONG_PW>@localhost:5432/qrdining
BACKUP_PROVIDER=r2
R2_ENDPOINT=https://<ACCOUNT_ID>.r2.cloudflarestorage.com
R2_BUCKET=qr-dining-backups
R2_ACCESS_KEY=<backups token Access Key ID>
R2_SECRET_KEY=<backups token Secret Access Key>
BACKUP_PREFIX=backups
RETENTION_DAYS=14
# Optional: emit Prometheus metrics for the BackupFailed / BackupTooOld alerts
NODE_EXPORTER_TEXTFILE_DIR=/var/lib/node_exporter/textfile_collector
Host dependency: the backup uses the aws CLI (storage_init requires aws on PATH). Install it on the production host: apt-get install -y awscli (or the official bundle). pg_dump/pg_restore v17 must also be present.

B · Image uploads — the app's environment (compose ./.env)

All five must be set together or the app treats R2 as disabled (uploads → 503). Optional for the soak.

R2_ACCOUNT_ID=<ACCOUNT_ID>
R2_ACCESS_KEY_ID=<uploads token Access Key ID>
R2_SECRET_ACCESS_KEY=<uploads token Secret Access Key>
R2_BUCKET=qr-dining-uploads
R2_PUBLIC_BASE=https://media.<your-domain>   # custom domain or r2.dev public URL for the uploads bucket

4 · Verification commands

Run these on the production host once the backup token is in backup.env. They exercise the exact aws s3 code path the script uses (--endpoint-url … --region auto).

# Load the backup credentials into the shell.
set -a; . /etc/qr-dining/backup.env; set +a
export AWS_ACCESS_KEY_ID="$R2_ACCESS_KEY" AWS_SECRET_ACCESS_KEY="$R2_SECRET_KEY"
AWS=(aws --endpoint-url "$R2_ENDPOINT" --region auto)

# (a) Credentials + bucket reachable (empty listing is fine).
"${AWS[@]}" s3 ls "s3://$R2_BUCKET/"

# (b) Write + read + delete round-trip.
echo "r2-ok $(date -u +%FT%TZ)" > /tmp/r2probe.txt
"${AWS[@]}" s3 cp /tmp/r2probe.txt "s3://$R2_BUCKET/_probe/r2probe.txt"
"${AWS[@]}" s3 cp "s3://$R2_BUCKET/_probe/r2probe.txt" /tmp/r2probe.back.txt
diff /tmp/r2probe.txt /tmp/r2probe.back.txt && echo "ROUND-TRIP OK"
"${AWS[@]}" s3 rm "s3://$R2_BUCKET/_probe/r2probe.txt"

5 · Backup test (live)

Run one real nightly backup and confirm the dump + manifest landed in R2.

cd /opt/qr-dining/backend
set -a; . /etc/qr-dining/backup.env; set +a
./scripts/nightly-backup.sh
# Expect: [1/5]…[5/5] then "OK: backup complete -> backups/YYYY/MM/backup_….dump"

# Confirm the object and the manifest exist in R2:
"${AWS[@]}" s3 ls "s3://$R2_BUCKET/backups/" --recursive | tail
"${AWS[@]}" s3 cp "s3://$R2_BUCKET/backups/manifest.jsonl" - | tail -1
The manifest line records timestamp, key, bytes, and sha256. Keep this output as the SEV-1 "live R2 round-trip" evidence.

6 · Restore test (live, to a throwaway DB)

Prove the backup is restorable — a backup you can't restore is not a backup. Restore into a disposable database, never production.

# Throwaway target (separate container/port; NEVER the production DB).
docker run -d --name r2-restore-test -e POSTGRES_PASSWORD=test \
  -e POSTGRES_USER=postgres -e POSTGRES_DB=restore_target -p 55444:5432 postgres:17-alpine

# Download the latest dump named in the manifest.
LATEST=$("${AWS[@]}" s3 cp "s3://$R2_BUCKET/backups/manifest.jsonl" - | tail -1 \
  | sed -n 's/.*"key":"\([^"]*\)".*/\1/p')
"${AWS[@]}" s3 cp "s3://$R2_BUCKET/$LATEST" /tmp/restore.dump

# Verify checksum against the manifest, then restore.
sha256sum /tmp/restore.dump
DATABASE_URL=postgres://postgres:test@localhost:55444/restore_target \
  ./scripts/restore.sh /tmp/restore.dump   # type 'yes' to confirm
# Expect: "Restore complete" + non-zero row counts for sessions/orders/payments/staff/menu_items/event_log

# Tear the throwaway down.
docker rm -f r2-restore-test
