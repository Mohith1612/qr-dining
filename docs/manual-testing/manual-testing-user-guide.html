1 · Guest journey trust domain: guest

The guest is the heart of the product: scan a table QR, join a session, collaborate on a shared cart, and (as host) order and pay.

1.1 Scan QR & create a session

  1. From the Dashboard, click a free Saffron House table (e.g. Bandra T3), or visit localhost:3000/table/<token>.
  2. The resolved table shows the branch and the Serene guest UI with its tenant theme (dark-luxury for Saffron House).
  3. Enter a display name (phone optional) and create the session. You become the host.
Expected
Session opens; the page shows your name as host; the table theme (colours) is applied; the menu is reachable.
Common failure modes
"Table not found" (wrong/expired token) · theme not applied (theme bridge) · scanning an occupied/idle table must join or resume the existing session (incl. payment_pending / awaiting_reactivation) — a SESSION_ALREADY_ACTIVE error here is the regression the occupied-table fix closed.
Verify
Returned session.session_token is empty in the network response (F-8 — credential never leaks). A host badge appears. session_number looks like SAFF-BND-S-YYYYMMDD-NNN.

1.2 Join an existing session (second guest)

  1. In a second browser, open the same table token (a seeded live table like Bandra T1, or a session you created on T3).
  2. Enter a different name and join.
Expected
Both participants appear in the presence list; the second joiner is not host; the shared cart is identical for both.
Common failure modes
Second guest sees an empty/different cart (cart not shared) · join silently creates a second session on the table.
Verify
One session, two session_participants rows; only one is_host=true.

1.3 Reconnect

  1. Mid-session, reload the page or toggle network off/on briefly.
Expected
A reconnecting banner appears, then state restores from the authoritative snapshot — cart, orders, and participants are intact. No duplicate orders.
Common failure modes
"Connection lost" dead-end (F-1) · cart empties on reconnect (snapshot refetches cart separately) · stale order statuses.
Verify
After reload the order tracker still shows current statuses; sequence numbers don't regress.

1.4 Order (host only)

  1. Add items to the shared cart from the menu.
  2. As host, place the order. As a non-host, confirm the "only the host can send orders" gate.
Expected
Order is created (pending), appears in the guest order tracker and on the kitchen display. Non-host cannot place it (UI disabled and server rejects).
Common failure modes
Non-host able to order (host gate is server-authoritative) · duplicate orders on double-tap (idempotency) · price drift after menu change (order snapshots price).
Verify
As the order advances (kitchen side) the guest tracker moves confirmed→preparing→ready→served without a manual refresh (F-6).

1.5 Payment & customer linking (host only)

  1. Open Pay, review the bill (subtotal/tax/total — an immutable snapshot is captured).
  2. Choose cash or UPI and initiate. Optionally opt in as a customer (name/phone).
  3. For cash/UPI the status becomes "awaiting confirmation" until a waiter settles.
Expected
Cart freezes (session → payment_pending); guest waits for real confirmation; on waiter settlement guest sees PAYMENT_COMPLETED and the session closes.
Common failure modes
False "payment success" before settlement · bill changes after initiation · session abandoned while payment pending (must not happen).
Verify
No fabricated settlement — the guest only completes after a staff/webhook event. Customer opt-in creates/links a customers row.

2 · Participant journey guest (non-host)

Expected
Shared cart: any participant adds/removes items; everyone converges via CART_UPDATED refetch. Presence: joins/leaves update the list live. Reconnect: a participant reload restores the same shared session.
Common failure modes
Cart diverges between participants · a left participant still shown present · participant accidentally gets host powers.
Verify
Add an item as participant B → it appears for host A within ~1s. Host hand-off (host leaves) reassigns host via HOST_CHANGED; the new host gains ordering rights. Also test the manual path: the host's "Make host" control transfers the role to another participant (refused while payment_pending — HOST_TRANSFER_LOCKED).

3 · Waiter journey staff · pin 3333

  1. Login at /staff/login with branch_id 1 (Bandra) and PIN 3333 → waiter dashboard.
  2. Three queues: assistance, ready-to-serve orders, pending payments (the seeded T2 payment shows here).
  3. Acknowledge then resolve an assistance request; mark a ready order served; settle a pending cash payment.
Expected
Settling a payment completes it, notifies the guest (PAYMENT_COMPLETED), and closes the session. Serving moves the order out of the ready queue.
Common failure modes
Pending-payments queue empty when it shouldn't be (seeded T2) · waiter can advance cooking states (kitchen-only) · settlement doesn't reach the guest.
Verify
The seeded "awaiting confirmation" payment on each primary branch's T2 is visible and settleable. After settle, payments.status=completed and settled_by_staff_id is set.

4 · Kitchen journey staff · pin 4444

  1. Login with branch_id 1, PIN 4444 → KDS Kanban (pending / confirmed / preparing / ready).
  2. Advance the seeded confirmed order: confirmed→preparing→ready. Note kitchen cannot mark served.
Expected
Each transition pushes a WS event; the guest tracker and waiter queue update live. "Served" is absent/blocked for kitchen.
Common failure modes
Kitchen able to serve (waiter-only, server-enforced) · elapsed-time colouring stuck · order skips states.
Verify
Try to PATCH an order to served as kitchen → server rejects. Order only reaches ready from the kitchen.

6 · Owner / Organization owner staff owner · pin 1111

Saffron House is multi-branch, so its owner exercises real org governance. Login with branch_id 1, PIN 1111.

  • Branch governance: view/govern all three Saffron branches; cross-branch oversight.
  • Org analytics: aggregate across Bandra + Indiranagar + Connaught Place.
  • Audit: read the branch/org audit log (richer when AUDIT_LOG_V2_ENABLED is on).
  • Everything a manager can do, plus the above.
Expected
Org analytics sum the three branches; a single-branch owner (Copper Pot / Urban Brew) sees only their one branch.
Common failure modes
Org owner sees another org's branches (cross-tenant leak) · org analytics include only the primary branch.
Verify
Saffron owner cannot see Copper Pot or Urban Brew branches/data anywhere.

9 · Multi-instance realtime app-1 ⇄ app-2

  1. Guest: open a Saffron table on Frontend A (:3000 → app-1), create a session, add a cart item.
  2. Staff: open Frontend B (:3001 → app-2), log in as kitchen/waiter for branch 1.
  3. Place an order on A; advance it on B; watch both update.
Expected
Events cross instances both ways (shared Postgres + Redis + guest-token secret). A session created on app-1 is fully readable on app-2 with the same guest token.
Common failure modes
Events only visible on the originating instance (Redis pub/sub not shared) · guest token rejected on the other instance (secret mismatch) · CSP blocks the cross-port WS (dev allows localhost).
Verify
Order placed on A appears on B's KDS within ~1s and vice-versa. (Pre-verified at the API layer: app-1 create → app-2 snapshot returns HTTP 200.)

10 · Cross-tenant isolation Alpha / Beta / Gamma

  1. As Saffron owner (branch 1), attempt to view Copper Pot (branch 4) or Urban Brew (branch 5) data anywhere — branches, menu, sessions, analytics, audit.
  2. Take a Saffron guest token and try to read a Copper Pot session/snapshot.
  3. In platform analytics, confirm per-org figures don't merge tenants.
Expected
Every cross-tenant attempt is denied or scoped out. A guest token is bound to its own session/branch/org and cannot read another tenant's session (the T-01 class of bug must not reproduce).
Common failure modes
Snapshot of session A returns data when queried with a token from a different session/tenant · branch-scoped admin lists another branch · analytics aggregate across orgs.
Verify
Saffron token on a Copper Pot session → rejected. Owner of one org never sees another org's branches.

11 · Security

  • Trust-domain rejection: staff token on a /platform/* route → rejected; guest token on staff routes → rejected.
  • Token tampering: mutate a guest token byte → validation fails; revoke participant → credential-version bump invalidates token.
  • Lockout / rate limits: repeated bad staff PINs → lockout; hammer /staff/auth or /platform/auth → fail-closed sensitive rate limit (10 rpm).
  • Host gating (server): non-host order/payment attempt rejected server-side even if the UI is bypassed.
  • Body-size limit: >1 MB body → rejected.
Verify
Each control fails closed. Rate limiting on auth routes stays enforced even under Redis pressure.
