1. What this product actually is

QR-Dining is a session-centric, realtime, multi-tenant dine-in operating system. A guest scans a QR code glued to a physical table. From that instant the table session — not the diner, not the order — is the unit of truth.

This is the single most important idea in the codebase. Almost every bug class you will hunt is a violation of it. Concretely:

  • Several guests join one session and share one live cart over WebSockets.
  • Exactly one participant is the host. Only the host may submit the order, request the bill, or initiate payment. Everyone else can browse and add to the cart. This is deliberate anti-chaos design for group dining, and it is the #1 source of "is this broken?" confusion in the field.
  • Staff (waiter / kitchen / manager / owner) work a PIN-authenticated console that polls REST every 10 seconds — deliberately not realtime. Guests are realtime; staff are not.
  • A completely separate platform trust domain (super admin / support / billing / auditor) governs tenants, entitlements, flags, themes, billing and support. Almost all of it is intentionally in shadow / observe-only mode.

Who it serves

  1. Dine-in restaurants in India. INR default, UPI/cash/card-manual payment reality, Oracle Cloud Ampere arm64 cost profile. No app install for the guest.
  2. Groups of diners. The collaborative shared-cart/host model is built for a table of six, not a solo QR menu.
  3. A future platform operator (you). The console, entitlements, billing and support tooling are the skeleton of a SaaS business, currently running dark.

What differentiates it — and therefore what must not break

  1. The session state machine — 6 states, enforced transitions, cart frozen during payment_pending, reactivation instead of silent expiry.
  2. Collaborative ordering — shared cart, host-gated submission, live presence.
  3. Operational honesty — payment escalation never mutates state; the audit log is trigger-immutable; every risky behaviour sits behind a reversible flag.
  4. Rollout discipline — shadow before strict, metrics that must read zero before a flag flips.

                    PostgreSQL 17     Redis 7 (AOF, 256MB LRU)
                    (AUTHORITATIVE)   pub/sub · presence · cache ·

                          │           worker locks · escalation dedup

Postgres is authoritative for everything; Redis is disposable. Chaos-validated: a sustained Redis outage degrades gracefully — realtime pauses, HTTP keeps working, sensitive rate limiters fail closed — and recovers by itself. App restart recovery is ~12s with idempotent migrations at boot. This is a property you should personally verify (§14).

Middleware chain — order matters

Recover → [otelgin] → RequestID → audit → Logger → Metrics → SecurityHeaders → CORS → MaxBodySize(1MB) → Tenant, then per-group rate limits and auth (StaffAuth, PlatformAuth, BranchTenantGuard).

Two consequences you can observe: a panic in any handler returns a clean 500 and never kills the process; and every response carries an X-Request-ID, with the access log also carrying trace_id when tracing is on.

3. Three trust domains that must never mix

DomainMechanismRolesWhat must be true
Guest Bespoke HMAC-SHA256 signed token (not a JWT — no alg header, so immune to alg-confusion). Claims: session / branch / tenant / org / participant / credential-version / exp / jti. Audience qr-dining-guest, 12h TTL. participant, host A token from session A must never read session B. WS admission requires a single-use Redis ticket.
Staff PIN login → opaque DB-backed session token (staff_sessions). Brute-force lockout + 10 RPM sensitive limiter that fails closed. owner, manager, waiter, kitchen Branch-scoped absolutely. A staff token must be rejected by every /platform/* route.
Platform Email+password → optional TOTP MFA (AES-GCM encrypted secrets) → opaque platform session. middleware/platform_auth.go explicitly rejects staff tokens. super_admin (global bypass), support_admin, billing_admin, read_only_auditor Tenant-agnostic but fully audited. The frontend keeps three separate bearer tokens that are never mixed (frontend/lib/api/client.ts). In local dev it also sends X-Tenant-Slug.

Verify this yourself Copy a staff bearer token out of devtools and call GET /platform/organizations with it → must be 401. Copy a guest token from session A and call GET /sessions/<B>/snapshot → must be refused, never data. These are the two cheapest tenancy proofs in the product.

Central authz engine — shadow mode

internal/authz/ evaluates every guarded action, but AUTHZ_CENTRAL_POLICY_ENFORCE=false means a denial is recorded and then allowed (the audit row shows success with a shadow note; policy_shadow_mismatch_total increments). Per-handler role checks are what actually enforce today. So: if a role check is missing in a handler, the shadow engine will not save you. Test RBAC as if the engine did not exist.

Invariants you are certifying — never change casually

  1. The transition table is law. Every worker, handler and the frontend's terminal-state screens assume it. payment_pending can never be bypassed by lifecycle automation.
  2. One active session per table (DB constraint). The joinability predicate must stay aligned with it — misalignment was certification finding #11.
  3. Bill snapshot immutability. The bill a guest agreed to is frozen at payment initiation. Promos and loyalty never retroactively edit it.
  4. Audit log immutability, enforced by the DB trigger trg_audit_log_immutable.
  5. Loyalty ledger append-only, signed points, CHECK (points_balance >= 0), earn-idempotent per payment.
  6. Webhook idempotency via payment_webhook_events.

6. Guest surface — page by page

Route group (guest). Design system: Serene — alabaster #FAF9F5, charcoal ink, Hanken Grotesk + Cormorant Garamond. This is the only surface that gets tenant theming.

6.1 /table/[token] — QR landing

Why it exists
Turns a physical sticker into a digital session. The only unauthenticated entry point to the whole guest experience.
Who uses it
Every diner, every time. Zero prior knowledge assumed.
How to access
https://qr-beta.mohith16.com/table/<qr_code_token> — live tokens on the dashboard.
Permissions
None. The token is the credential.
Endpoints
GET /tables/by-qr/:token → GET /branches/:id/theme → then either POST /sessions (create) or POST /sessions/:id/join.

What every control does

  • Name field (required) — becomes session_participants.display_name, shown on shared cart lines.
  • Phone field (optional) — links a customers row (UNIQUE(restaurant_id, phone_e164)), the loyalty opt-in hook. Invalid input → INVALID_PHONE with a friendly inline message, not a crash.
  • Continue — the branch point. If the table already has a non-terminal session the copy flips to "Join the party" and it calls join; otherwise it calls create.

State & data changes

Create: new sessions row (status active, number allocated from session_sequences), a session_participants row flagged host, tables.status → occupied, an empty carts row, and SESSION_CREATED published. Join: only a participant row + a PARTICIPANT_JOINED broadcast. Both return a guest_access_token persisted to localStorage.

Observability

Trace: POST /sessions root span with child pgx INSERT spans and a redis PUBLISH span. Metrics: active_sessions_total ↑, http_requests_total{route="/sessions"} ↑. The log line carries trace_id + request_id; an audit row records the creation.

Specifically verify
  • Theme paints instantly in tenant colours (no white flash), then refines. Compare Saffron (dark-luxury), Copper Pot (warm-cafe), Urban Brew (vibrant).
  • A garbage token shows "This QR code is invalid or has expired." — never a stack trace or blank page.
  • Joining an existing session shows the join copy and lands you in the same session id as the first guest.
  • Scanning a table whose session is payment_pending: you join (reads allowed) but find the cart frozen.
  • Editing the session UUID in the URL to another session's id must be rejected.

What could go wrong

The classic failure is TABLE_OCCUPIED / SESSION_ALREADY_ACTIVE when the joinability predicate disagrees with the one-active-session-per-table constraint. Also watch for a stale seeded session making a "free" table unusable — that is environment state, not a bug (§16).

6.2 /session/[id] — session home

Why
The hub: presence, host identity, popular-items carousel, navigation to menu/cart/orders/payment.
Endpoints
GET /sessions/:id/snapshot (via SessionProvider), GET /branches/:id/menu, POST /sessions/:id/host, GET /branches/:id/theme.

What every control does

  • Participant avatars — live presence from Redis TTL keys refreshed by WS pings. A guest who closes their browser should fade out within the presence grace (60s default).
  • Host transfer — POST /sessions/:id/host, broadcasts HOST_CHANGED. Rate-capped 6/min/session. Only the current host may hand off.
  • Popular items carousel — featured menu items; tapping deep-links into the menu.
  • Nav to Menu / Cart / Orders / Bill.
Specifically verify
  • Open the same session on two devices. Both see both avatars. Transfer host on A → B updates within a second, B gains the "Send order" affordance and A loses it.
  • SessionProvider owns terminal-state screens: close the session from staff → both guests get "session ended", not a 404.
  • Hard-refresh mid-session → snapshot reload restores identical state (backend-authoritative recovery).

6.3 /session/[id]/menu — menu & item detail

Endpoints
GET /branches/:id/menu (Redis-cached), POST /sessions/:id/cart/items
  • Category tabs / scroll spy — client-side, from menu_categories.
  • Item card → detail dialog — quantity stepper, modifier groups, notes. Multi-select groups allow many; single-select groups allow exactly one (migration 000037), and violating that returns MODIFIER_CONFLICT.
  • Add to cart — writes cart_items, publishes ITEM_ADDED + CART_UPDATED to every participant.
  • Unavailable items — greyed, not addable. Toggling availability from admin broadcasts MENU_ITEM_AVAILABILITY_CHANGED live.
Specifically verify
  • Add an item on device A → it appears on device B without refresh, attributed to A's name.
  • Toggle an item unavailable in admin while a guest holds it in the cart → guest sees the event; placing the order must fail cleanly with MENU_ITEM_UNAVAILABLE, not a 500.
  • Change a price in admin; note how long the menu takes to reflect it (Redis cache) and whether it invalidates immediately.
  • Items with and without images both render. Check the images-left / images-right / card layout variants from the redesign.

6.4 /session/[id]/cart — the shared cart

Endpoints
GET /sessions/:id/cart, DELETE /sessions/:id/cart/items/:item_id, POST /sessions/:id/orders
  • Line items grouped by who added them.
  • Remove — ITEM_REMOVED + CART_UPDATED broadcast.
  • Send order — HOST ONLY. Non-hosts get NOT_SESSION_HOST. Creates orders + order_items, allocates a number from order_sequences, empties the cart, publishes ORDER_PLACED. Rate-capped 12/min/session.
Specifically verify
  • Non-host sees a clear explanation, not a dead button. This is the #1 predicted field support ticket.
  • Double-tap "Send order" fast → exactly one order. Check idempotency_replays_total.
  • Empty cart → CART_EMPTY.
  • During payment_pending, add/remove/order must all fail with PAYMENT_IN_PROGRESS.

6.5 /session/[id]/orders — live order tracker

Reads GET /sessions/:id/orders and updates from ORDER_CONFIRMED / PREPARING / READY / SERVED / CANCELLED. Each order shows its human-readable number, items with modifiers, and a status timeline.

Specifically verify Drive the order from the kitchen console and watch the guest tracker advance without refresh at every step. Then cancel an order from staff → the guest sees it cancelled and the bill excludes it.

6.6 /session/[id]/payment — bill & payment

Endpoints
GET /sessions/:id/bill, POST /sessions/:id/promos/validate, POST /sessions/:id/payments
  • Bill breakdown — subtotal, discount, tax, service, tip, total, and the source order IDs.
  • Promo code → Apply — POST /sessions/:id/promos/validate previews the discount and broadcasts PROMO_APPLIED. The redemption itself is recorded at payment.
  • Tip selector — folded into the snapshot at initiation.
  • Payment method — cash / card_manual → requires_staff_confirmation; digital → provider_pending; upi → either, by config.
  • Pay / Request bill — HOST ONLY. Freezes a bill_snapshots row, moves the session to payment_pending, publishes PAYMENT_INITIATED (which freezes every participant's cart UI). Rate-capped 6/min/session plus a 30/min sensitive limiter.

Split payments

Multiple payments rows per session are supported. The session auto-closes only when completed payments cover the bill (maybeCloseSettledSession). Partial settlement must leave the session open.

Specifically verify
  • Bill snapshot immutability: initiate payment, then have staff change a menu price or deactivate the promo. The frozen bill must not move. This is the payment-correctness cornerstone.
  • Non-host cannot initiate.
  • Two payments covering half each → the session closes only after the second completes.
  • Promo applies at payment, not at order: the order confirmation shows pre-discount pricing, the bill post-discount.
  • Leave a payment unsettled 5 minutes → warn escalation; 15 minutes → critical. Confirm no state changed, only alerts.

6.7 /session/[id]/assist — call the waiter

POST /sessions/:id/assist, capped 6/min/session. Creates an assistance_requests row and publishes ASSISTANCE_REQUESTED. The guest sees acknowledgement, then resolution, as the waiter acts.

Specifically verify Spam the button — after 6 you must get a clean rate-limit message, not a broken UI. Then confirm the waiter board shows the request within one poll cycle (≤10s).

6.8 Cross-cutting guest components

  • SessionTimeoutBanner — the "still here?" banner. Its buttons call POST /sessions/:id/reactivate and POST /sessions/:id/assist. Appears on SESSION_EXPIRING_SOON and in awaiting_reactivation.
  • CustomerOptIn — POST /sessions/:id/customer, links the phone to a customers row. With loyalty off it must degrade gracefully (FEATURE_DISABLED).
  • Terminal-state screens — owned by SessionProvider for closed / abandoned / expired.

7. Staff surface — login, waiter, kitchen

Route group (staff). Design system: Harmony — a static ops design (styles/surfaces.css, [data-surface="ops"]). Tenant theming deliberately does not apply here. That scoping decision structurally killed the "staff theme resets" bug class — so tenant colours bleeding into staff screens is a regression.

7.1 /staff/login

POST /staff/auth with branch_code + staff_code + pin. The beta requires all three fields; PIN-only/branch-ID payloads are rejected. A 10 RPM sensitive limiter that fails closed if Redis is down, plus a sliding-window brute-force lockout.

Specifically verify Enter a wrong PIN repeatedly → lockout engages with a clear message, and the correct PIN stays refused until the window passes. Confirm each role lands on its correct default page (kitchen → /staff/kitchen, waiter → /staff/waiter, manager/owner → /staff/admin).

7.2 /staff/waiter — the service floor

Endpoints
GET /branches/:id/orders/active · GET /branches/:id/assist/active · GET /branches/:id/payments · PATCH /orders/:id/status · PATCH /assist/:id/ack · PATCH /assist/:id/resolve · PATCH /payments/:id/settle
Refresh
REST poll every 10s. No WebSocket. Expected.

Every button

  • Mark served — ready → served. The only place this transition happens; it was deliberately removed from the kitchen board.
  • Acknowledge assistance — pending → acknowledged, broadcast to the guest.
  • Resolve assistance — → resolved.
  • Settle payment — on a requires_staff_confirmation payment → completed. Stamps payments.settled_by_staff_id (the field staff analytics later derives from), publishes PAYMENT_COMPLETED, and may close the session.
Specifically verify
  • Settling a cash payment closes the session and the guest sees the terminal screen within a second — the guest is realtime even though you are not.
  • Two waiters settling the same payment concurrently → exactly one succeeds; the other gets a clean invalid-transition error.
  • The board shows only this branch's work. Log in as the Bandra waiter; Indiranagar sessions must be invisible.

7.3 /staff/kitchen — the KDS

Endpoints
GET /branches/:id/orders/active · PATCH /orders/:id/status
  • Columns: confirmed → preparing → ready, with item-level detail, modifiers and notes.
  • Confirm — pending → confirmed where the flow starts at pending.
  • Start preparing — confirmed → preparing.
  • Mark ready — preparing → ready. The card then leaves the kitchen board; the waiter owns "served".
Specifically verify
  • Latency: a guest order appears within ≤10s. Time it. 30s is a finding.
  • Modifiers and item notes are legible — a real cook reads this at arm's length.
  • No payment or table affordances exist on this surface.
  • Leave the tab open 20 minutes; the poll must not leak memory or stack duplicate cards.

10. Every feature flag, individually

There are two entirely separate flag systems. Confusing them is the most common mistake.

  1. Env strict-rollout flags (9, plus tracing) — process-level booleans read once at boot from the environment (backend/internal/config/config.go). Changing one requires a restart. They gate security and correctness enforcement.
  2. Platform product flags (2 seeded) — rows in platform_feature_flags, resolved per request with branch > org > global > default. They gate product features, combined with entitlements.

12. Realtime — events, ordering, recovery

Connection lifecycle

  1. Guest authenticates → POST /sessions/:id/ws-ticket → a short-lived, single-use Redis ticket.
  2. Connect GET /ws with the ticket. The hub is a single goroutine with no mutexes — the rooms map is owned by one loop.
  3. Events flow service → Redis pub/sub → hub subscriber → room broadcast.

Ordering & reconciliation — the core principle

Every session has a monotonic sequence (session_sequences). The client tracks the last sequence it saw; on reconnect it fetches GET /sessions/:id/snapshot (advertised via the X-Reconnect-Endpoint header) and reconciles.

The snapshot is authoritative; events are advisory. If UI state survives a refresh but disagrees with the snapshot, the client has invented state — a genuine bug.

Reconnect behaviour

  • Client: exponential backoff 1s → 30s, max 10 attempts, 30s ping interval.
  • Server: 12 admissions per minute per session; the rest 429 (chaos-validated storm bound).
  • A ticket 409 routes through snapshot reactivation.
  • Exhausting retries leaves the current UI visible with an explicit in-place Retry — not a dead end. (Finding F-1 was exactly a reconnect dead-end; this is its regression test.)
  • Slow consumers are evicted immediately (non-blocking send) — one slow phone cannot stall a table.
  • 100-strike force-close on inbound abuse.

14. Failure scenarios worth testing by hand

Grouped by what they prove. Severity guidance lives in the checklist.

Network & transport

  1. Wi-Fi off mid-session → reconnect banner, exponential backoff, then snapshot reconciliation. No lost cart items.
  2. Airplane mode 3+ minutes → the session may move to awaiting_reactivation; returning should offer reactivation, never a dead end.
  3. Collector/Redis/Postgres/backend outage injection is isolated-local-only. Mark these N/A in a beta-only run; never stop shared-VM services without a separate operator window.
  4. Cross-instance: create/mutate through qr-api-beta-1 and read through qr-api-beta-2, then reverse the direction. Repeat the WebSocket ticket/event path both ways.

Client-side

  1. Browser refresh at every step of the guest flow.
  2. Back/forward navigation, including back into a closed session.
  3. Two tabs, same guest → consistent, with no duplicate participant.
  4. localStorage cleared mid-session → treated as unauthenticated, no silent host escalation.
  5. Deep-link straight to /session/<id>/payment without going through the QR.
  6. Mobile viewport (375×812) on every guest page — this is a phone product first.
  7. Slow 3G throttling on the menu page.

Concurrency

  1. Two guests add the same item simultaneously.
  2. Double-tap "Send order" → exactly one order.
  3. Two waiters settle the same payment → one wins cleanly.
  4. Kitchen advances an order the waiter is cancelling → invalid-transition error, no corruption.
  5. Host transfer while the old host is mid-submit.
  6. Two guests scan the same free table at the same moment → one creates, one joins; never two sessions.

Permissions & tenancy

  1. Non-host attempts order / bill / payment → NOT_SESSION_HOST with helpful copy.
  2. Manager attempts staff creation → refused (intended).
  3. Kitchen attempts payment settlement → refused.
  4. Cross-tenant: a Saffron staff token against a Copper Pot branch id → refused.
  5. Cross-session: guest A's token against session B → refused.
  6. Staff token against /platform/* → 401.
  7. read_only_auditor attempts any platform mutation → 403.
  8. Revoked staff session replayed after logout or deactivation → 401.
  9. Expired guest token, or one with a bumped credential version → refused.

State machine & money

  1. Cart mutation during payment_pending → PAYMENT_IN_PROGRESS.
  2. Bill snapshot immutability — change prices/promos after initiation; the frozen bill must not move.
  3. Split payment covering half → session stays open; the second payment closes it.
  4. Cancel a payment, then re-initiate → a new snapshot and clean state.
  5. Order cancelled after the bill was frozen → the frozen bill still governs.
  6. Webhook replay — the same signed event twice → one state change, the second recorded as a replay.
  7. Webhook with a bad signature / wrong amount / wrong currency / wrong session → all four rejected.
  8. Session timeout — set session_timeout_minutes to 1 in Settings and watch StaleSessionCleaner abandon the session and free the table.
  9. Payment escalation at 5 and 15 minutes → alerts only, zero state change.

Governance, themes & QR

  1. Flag precedence branch > org > global > default, all four layers.
  2. Entitlement AND flag truth table for both gated features.
  3. Suspend an org → guests keep ordering (inert by design).
  4. Theme change → repaints the guest surface only; staff and platform unaffected.
  5. Invalid theme token (bad hex, non-allowlisted key, javascript:) → rejected server-side.
  6. Theme never persists across a branch switch — no cross-tenant colour leak.
  7. QR refresh → the old token dies immediately.
  8. Deleted or archived table's QR → clean error.
  9. Printed QR scanned from paper with a real phone camera, all five collateral formats.
  10. Rate limits: assistance 6/min/session · order 12/min/session · payment init 6/min/session · host transfer 6/min/session · ws-ticket 12/min/session · staff auth 10/min — each must degrade to a clean message.

15. Recommended testing order — and why

0. Environment sanity           (10 min)
        ↓
1. GUEST happy path             (60 min)   ← generates the data everything else needs
        ↓
2. KITCHEN                      (30 min)   ← consumes guest orders
        ↓
3. WAITER                       (45 min)   ← closes the loop: serve + settle
        ↓
4. MANAGER / OWNER admin        (90 min)   ← configures what guests see next round
        ↓
5. PLATFORM control plane       (90 min)   ← governs what the tenant may do at all
        ↓
6. FLAGS + ENTITLEMENTS         (60 min)
        ↓
7. CROSS-TENANT isolation       (45 min)
        ↓
8. FAILURE scenarios            (90 min)   ← destructive; only after happy paths pass
        ↓
9. OBSERVABILITY pivot          (30 min)
        ↓
10. REGRESSION sweep            (45 min)   ← re-run step 1 after everything you changed

Why this order and not another

Guest first
It is the only role that creates data. Every other surface consumes sessions, orders, payments and assistance requests. Testing the kitchen board before any order exists is testing an empty state.
Kitchen before waiter
The order machine is directional: kitchen owns confirmed→preparing→ready, the waiter owns ready→served. You cannot test "mark served" until the kitchen has produced a ready order.
Waiter before admin
The waiter closes sessions through settlement, and settled sessions are what populate stats, performance and loyalty — the admin surfaces you test next. Analytics on zero closed sessions tells you nothing.
Admin before platform
Admin changes are tenant-local and reversible; platform changes are global and can invalidate everything you already tested. Establish the tenant baseline first.
Flags after both consoles
You need a working feature to prove a gate turns it off. Testing the gate first cannot distinguish "gated" from "broken".
Cross-tenant after single-tenant
An isolation failure is only meaningful once the happy path works; otherwise you cannot tell isolation from a plain bug.
Failure scenarios late
They are destructive — Redis outages, killed backends, expired sessions. Running them early poisons the data your happy-path tests depend on.
Observability near the end
It needs a rich trace and audit history to pivot through, and it is the fastest confidence check that everything you just did was recorded.
Regression sweep last
You have changed themes, flags, entitlements, menus, timeouts and plans. Re-run the guest happy path to prove your own configuration did not break it. This step catches more real bugs than any other.
Two people? Guest and staff flows are naturally two-handed. One person on a phone as the guest, one on a laptop as staff, in the same room, is worth several hours of solo tab-switching — especially for realtime latency, which is what a real service actually feels.
