1 · Recommended Window Setup

Use separate browser windows (or profiles) per role — guest and staff identities live in per-tab sessionStorage, so a stray shared tab can swap identities under you. Windows 1–2 use different profiles/incognito so the two guests are genuinely distinct devices. Window 4 deliberately runs on Frontend B so the core service loop exercises multi-instance realtime all day.

Saffron House · Bandra T3 (free table). Enter a name → you become host. Expect the Serene guest UI (Saffron tenant theme: dark-luxury), a host badge, menu reachable, cart shared. No login — the QR token is the entry.

4 · Recommended Certification Order

Phases are ordered so foundation bugs surface before they can poison later phases, and so state created early (orders, payments, customers, audit rows) becomes the test data for later phases. Total: ≈ 6–7.5 focused hours — a full day with breaks, or split A–C / D–F across two half-days.

Phase A — Guest experience 75–90 min

Goals
  • Full guest loop on Saffron Bandra: QR scan → create → second guest joins → shared cart → host orders → live tracking → cash/UPI payment initiation.
  • Re-scan behaviors: occupied table (joins), idle table (resumes), payment_pending table (join allowed).
  • Manual "Make host" transfer; reconnect (reload mid-session); idle into awaiting_reactivation and recover.
  • Repeat a compressed pass on Urban Brew (br.5) to confirm the vibrant theme + free-plan tenant behaves identically.
Critical observations
  • session_token is empty/absent in every guest network response (DevTools → Network) — F-8.
  • Order tracker advances without refresh (F-6); cart converges between windows ≤1s; only one is_host.
  • Non-host order/pay blocked in UI and rejected by the server if forced (edit the request).
Common failure signs
  • SESSION_ALREADY_ACTIVE on re-scan of an occupied/idle table (regression of the occupied-table fix).
  • "Connection lost" dead-end after idle (F-1 regression) · cart emptied after reload · duplicate order on double-tap.
  • Theme not applied on entry, or one tenant's colours bleeding into another tab.

Phase B — Waiter + kitchen operations 60–75 min

Goals
  • Window 4 (kitchen on Frontend B) advances Phase A's order pending→confirmed→preparing→ready; Window 3 (waiter on A) serves it and settles the payment — the loop crosses both backend instances.
  • Assistance: guest requests → waiter ack → resolve, latency observed.
  • Settle the seeded pending payments on Copper Pot (br.4) with its own waiter (PIN 3333 @ 4).
  • Role boundaries: kitchen cannot serve; waiter cannot advance cooking states.
Critical observations
  • Every transition lands on the guest tracker live, across instances, both directions.
  • Settlement closes the session, frees the table, sets settled_by_staff_id; guest sees real completion only after staff settles (no fake success).
  • The two seeded stalled payments will be emitting alert-only escalations in the logs — they must never auto-settle or auto-cancel.
Common failure signs
  • Order placed on app-1 never reaches the app-2 KDS (Redis fan-out broken) — this environment is the only place multi-instance is exercised.
  • Stale queues needing manual refresh · settlement succeeds but guest stays "awaiting confirmation" · table not freed after close.

Phase C — Manager / owner workflows 75–90 min

Goals
  • Menu CRUD + modifiers + availability toggles (watch a seated guest live); staff create/rotate-PIN/deactivate; tables + QR refresh.
  • Promos incl. the per-guest limit: no phone → PROMO_PHONE_REQUIRED; cap enforced per phone.
  • Performance and Loyalty tabs: verify the gated empty states (403 codes in Network tab) as owner AND that waiter/kitchen get the role message.
  • Collateral studio (staff side), Appearance tab, Stats (plan-gated by tier: Saffron yes, Urban limited); owner-only org governance + org analytics + audit reads across the 3 Saffron branches.
Critical observations
  • Branch isolation: a Bandra menu edit never appears in Indiranagar; manager cannot reach org governance (owner-only).
  • QR refresh: new token resolves, old token 404s.
  • Audit rows appear for staff mutations (audit v2 is on in this stack).
Common failure signs
  • Gated tabs crash or show spinners forever instead of clean empty states.
  • Manager staff-add UI offering roles the backend then rejects (finding #7 — now create-staff is owner-only/manager-gated; confirm).
  • Promo applied at the cart instead of the bill (promo moved to payment initiation in Phase-0 — it must appear on the bill).

Phase D — Platform operations 90–120 min

Goals
  • Orgs: list 3, create a 4th (org+restaurant+branch+tables+owner), suspend/activate (status flips; resolve-only).
  • Plans & entitlements: catalog shows the new keys (analytics.staff_performance, loyalty.*); assign plans; set org overrides.
  • Feature flags: catalog shows staff_performance_analytics + loyalty (default off); exercise global→org→branch precedence.
  • Subscriptions + billing: status transitions (valid only), invoices, billing profile; platform analytics (usage/revenue/health + the new staff-performance read).
  • Themes (change Urban's preset → its guests adopt it live), platform collateral studio, MFA enroll/confirm/challenge/disable on a platform user.
  • Support console as support@: search, session/order/payment detail (sanitized — no session_token/device_fingerprint), dual audit rows; sub-role separation (billing@ blocked from support, auditor@ read-only).
  • Optional deep-dive: grant the loyalty entitlements + flag to one tenant, enable customer_memory_enabled, run a paid session with opt-in, and watch points accrue + redeem. Gate flips take ≤60s (gate cache).
Critical observations
  • Staff tokens rejected on /platform/*, platform tokens rejected on staff routes (trust-domain walls).
  • Every platform read/mutation produces platform-audit entries; deep support reads produce tenant-visible critical audit rows.
  • MFA misconfig path returns 503 MFA_NOT_CONFIGURED, never 500 (PT-03).
Common failure signs
  • Theme edits from the staff Appearance tab and the platform Themes page fighting each other (two write-paths — staff writes legacy settings_json.theme, platform writes tenant_themes; platform wins on read).
  • billing_admin reaching support detail pages · auditor able to mutate · invoice/subscription state machine accepting an illegal transition.

Phase E — Cross-tenant security 60–75 min

Goals
  • Saffron staff/owner can never read Copper Pot/Urban data (dashboards, analytics, audit, menu admin — try forced branch_ids in URLs/API).
  • Guest token from a Saffron session replayed against a Copper Pot session/snapshot → rejected (T-01 class).
  • Snapshot matrix: own token OK · no token rejected · other-session token rejected · session_token stripped.
  • Token tampering (flip a byte), guest token on staff routes, staff on platform routes, oversized body (>1 MB), rapid-fire auth (lockout + 429s, fail-closed).
  • Theme/collateral/flags resolved per tenant only; platform analytics per-org filter never merges tenants.
Critical observations
  • Rejections are clean 401/403/404 JSON errors with stable codes — never 500s, never partial data.
  • Authz denials appear in the audit stream.
Common failure signs
  • Any cross-tenant 200 — stop and capture immediately; this class (T-01) was the worst historical bug.
  • 500s on malformed/forged input (validation should fail closed, not crash).

Phase F — Failure recovery 60–75 min

Goals
  • Reload mid-session, network toggle, and laptop-sleep style idle → snapshot reconciliation each time.
  • Kill one backend (kill the :8095 pid) mid-session: clients on B reconnect/fail over after restart; app-1 unaffected; restart and confirm recovery. Only ever the mtest binaries.
  • Redis flush (docker exec manual-testing-redis redis-cli FLUSHALL): presence/tickets/staff sessions reset (staff re-login expected), business data intact, guests re-snapshot.
  • Lifecycle clocks: a quiet session → awaiting_reactivation (~1 min) → return within ~5 min recovers it; past the window → abandoned, table freed by the reconciler.
  • Terminal sessions readable for 60 min, gone after (410-style).
Critical observations
  • No duplicate orders after any recovery (idempotency); sequence numbers never regress; cart refetches rather than trusting stale state.
  • A session with a non-terminal payment is never abandoned by the workers.
Common failure signs
  • Reconnect gives up permanently after ~10 attempts (~2 min of outage) — known WS retry ceiling; document anything that strands a guest.
  • Stranded occupied tables after abandonment · "payment completed" appearing without settlement after recovery.

5 · Things Most Likely To Break

Ranked from the pilot dress rehearsal, remediation history, readiness audits, and rollout history. HIGH = watch actively every phase · MED = check deliberately once · LOW = note if seen.

HIGHReconnect / reactivation edges.
The F-1 dead-end was fixed, but presence/reactivation timing (finding F-2) is deliberately untuned for real dining. Idle a guest tab through every boundary (≈60s → awaiting_reactivation, ≈5 min → abandoned) and through the 10-attempt WS retry ceiling. Anything that leaves a guest stranded without a recovery affordance is a finding.
HIGHMulti-instance event fan-out.
The WS Hub is per-process; cross-instance delivery rides Redis pub/sub and is unproven at scale. This stack is the only place it's exercised — watch for one-directional updates (A→B works, B→A doesn't) and events lost during reconnect windows.
HIGHCross-tenant leakage (T-01 class).
The worst historical bug was a cross-org snapshot 200. It's fixed and tested, but every new surface since (support console, collateral, themes, billing, the new gated tabs) is a new opportunity. Force IDs in URLs/API calls in every phase, not just Phase E.
HIGHPayment-pending lifecycle traps.
The hardest state: cart frozen, session protected from abandonment, alert-only escalation. Try to break it — leave it stalled, reload, transfer host (must be refused), re-scan the table (join allowed), then settle. Any auto-settle/auto-cancel or fake guest success is a serious finding.
MEDWindowed promos (Phase-0 fix — verify).
Finding #10 is fixed: promo time-windows now compare in branch-local time and display HH:MM. Verify a lunch-window promo is valid at Indian lunch hours (no longer a silent fail). Promo is also applied at the bill, not the cart.
MEDTheme dual write-path.
Staff Appearance tab writes legacy settings_json.theme; platform writes tenant_themes (authoritative on read). Edit from both sides and confirm the platform value wins everywhere and nothing flip-flops.
MEDStaff management (C16 — verify).
Finding #7 addressed: the Staff tab now shows a roster with Reset PIN + Deactivate; create-staff is owner-only (hidden from managers); managers may reset only waiter/kitchen and cannot reset self; "Change PIN" self-service in the staff bar. Confirm these boundaries hold server-side.
MEDCustomer opt-in gate (known finding #6).
Opt-in returns FEATURE_DISABLED unless customer_memory_enabled is set on the restaurant. Check the guest UI handles it gracefully; flip it only for the optional loyalty deep-dive.
MEDNew gated tabs (Performance / Loyalty).
Newest UI in the build. The only acceptable behavior while gated: clean empty state + 403 code. Crashes, infinite spinners, or data leaking through the gate are findings. Also confirm payments complete with zero loyalty side effects.
LOWStale-data noise in logs.
The two seeded stalled payments emit warn/critical escalation lines every minute, forever — by design (alert-only). Don't mistake them for failures; the soak closure flagged exactly this signal-hygiene issue.
LOWAudit coverage gap.
Order placement emits no audit row (known, deliberate gap) — don't log it as a bug when auditing Phase C/D trails.
LOWUX backlog (findings #1–#4, #9 — mostly delivered in Phase-0).
Delivered: modifier single-select (radio + 422 MODIFIER_CONFLICT), landing tiles + Currently Popular, kitchen ticket item contents, menu image upload, promo HH:MM clarity, presence heartbeat (no more 30s "still here?" pop). Verify each; remaining polish (e.g. recurring expiry banner) is not a certification blocker.
