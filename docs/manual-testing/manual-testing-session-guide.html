Cross-instance session guide

A reproducible observation path. Record what happens; this page does not assert that the path passes.

  1. Reset and capture the seed output. Run ./scripts/manual-testing-up.sh --reset. The output supplies the current branch codes, PINs, IDs, and randomly generated table tokens. scripts/manual-testing-up.sh:49-53; backend/scripts/seed.go:769-786
  2. Open a guest table on Frontend A. Use http://localhost:3000/table/<current-token>. The table page resolves the token before loading the guest surface. frontend/app/(guest)/table/[token]/page.tsx:35-68
  3. Create the host session. The table flow calls session creation when there is no stored session for that table. frontend/app/(guest)/table/[token]/page.tsx:70-112
  4. Join from Frontend B. Open the same current table token at :3001. The two frontends target different backend processes that share PostgreSQL and Redis. scripts/manual-testing-up.sh:62-75,96-109
  5. Exercise the guest flow. Add items, place an order, request assistance, and open payment. The server registers the corresponding guest endpoints at session scope. backend/internal/server/server.go:212-260
  6. Observe from staff. Sign in at http://localhost:3001/staff/login with current seed output, then inspect active orders, sessions, assistance, and payments. Those branch views are staff-authenticated routes. backend/internal/server/server.go:279-286,386-415
  7. Confirm or cancel payment. Initiation enters requires_staff_confirmation; staff can settle or cancel through protected endpoints. backend/internal/services/payment.go:759-773; backend/internal/server/server.go:391-399
  8. Record results. Use the checklist and export it before resetting browser storage.

Do not infer realtime correctness only from the final screen. Clients reconcile with a full session snapshot after reconnect, so record which browser received live changes and which recovered through reconciliation. frontend/lib/ws/connection.ts:129-176; backend/internal/server/server.go:270-272
